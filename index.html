Notice two interesting facts:

  • Dave (emp_id = 4) has dept_id = 9, but there is no department 9.
  • HR (dept_id = 4) exists, but no employee belongs to it.

These two "orphan" rows are exactly what make LEFT, RIGHT, and FULL joins interesting.

2. INNER INNER JOIN

What it does

An INNER JOIN returns only the rows that have a matching value in both tables. If a row in the left table has no match in the right table (or vice versa), it is dropped.

Example

SELECT e.emp_id, e.name, d.dept_name
FROM employees e
INNER JOIN departments d
  ON e.dept_id = d.dept_id;

Result

emp_idnamedept_name
1AliceEngineering
2BobSales
3CarolMarketing

Why Dave and HR are missing

  • Dave's dept_id = 9 has no match in departments → dropped.
  • HR's dept_id = 4 has no match in employees → dropped.

3. LEFT LEFT JOIN (LEFT OUTER JOIN)

What it does

A LEFT JOIN returns all rows from the left table, plus the matching rows from the right table. If there is no match on the right, the right-side columns are filled with NULL.

Example

SELECT e.emp_id, e.name, d.dept_name
FROM employees e
LEFT JOIN departments d
  ON e.dept_id = d.dept_id;

Result

emp_idnamedept_name
1AliceEngineering
2BobSales
3CarolMarketing
4DaveNULL

Why Dave shows up with NULL

Dave is in the left table (employees), so he is always kept. There is no department 9, so dept_name becomes NULL.

Visual intuition

employees   LEFT JOIN   departments
   ┌───┐              ┌───┐
   │ A │              │ E │
   │ B │              │ S │
   │ C │              │ M │
   │ D │              │ H │
   └───┘              └───┘
        ┌──────────┐
        │ A-E      │
        │ B-S      │
        │ C-M      │
        │ D-NULL   │  ← Dave kept, dept is NULL
        └──────────┘
Tip: LEFT JOIN is the most common join you'll use in practice — for example, "list all customers, even those who have never placed an order."

4. RIGHT RIGHT JOIN (RIGHT OUTER JOIN)

What it does

A RIGHT JOIN returns all rows from the right table, plus the matching rows from the left table. If there is no match on the left, the left-side columns are filled with NULL.

Example

SELECT e.emp_id, e.name, d.dept_name
FROM employees e
RIGHT JOIN departments d
  ON e.dept_id = d.dept_id;

Result

emp_idnamedept_name
1AliceEngineering
2BobSales
3CarolMarketing
NULLNULLHR

Why HR shows up with NULLs

HR is in the right table (departments), so it is always kept. No employee has dept_id = 4, so emp_id and name become NULL.

Visual intuition

employees   RIGHT JOIN   departments
   ┌───┐              ┌───┐
   │ A │              │ E │
   │ B │              │ S │
   │ C │              │ M │
   │ D │              │ H │
   └───┘              └───┘
        ┌──────────┐
        │ A-E      │
        │ B-S      │
        │ C-M      │
        │ NULL-H   │  ← HR kept, employee is NULL
        └──────────┘
Note: RIGHT JOIN is rarely used because you can always rewrite it as a LEFT JOIN by swapping the tables. Some databases (e.g., MySQL) don't even support RIGHT JOIN directly.

5. FULL FULL JOIN (FULL OUTER JOIN)

What it does

A FULL JOIN returns all rows from both tables. Rows that match are combined; rows that don't match are kept with NULL on the side that has no match.

Example

SELECT e.emp_id, e.name, d.dept_name
FROM employees e
FULL JOIN departments d
  ON e.dept_id = d.dept_id;

Result

emp_idnamedept_name
1AliceEngineering
2BobSales
3CarolMarketing
4DaveNULL
NULLNULLHR

Why both Dave and HR appear

  • Dave has no matching department → kept with dept_name = NULL.
  • HR has no matching employee → kept with emp_id = NULL and name = NULL.

Visual intuition

employees   FULL JOIN   departments
   ┌───┐              ┌───┐
   │ A │              │ E │
   │ B │              │ S │
   │ C │              │ M │
   │ D │              │ H │
   └───┘              └───┘
        ┌──────────┐
        │ A-E      │
        │ B-S      │
        │ C-M      │
        │ D-NULL   │  ← Dave kept
        │ NULL-H   │  ← HR kept
        └──────────┘
Note: Not all databases support FULL JOIN natively. MySQL, for example, does not — you can simulate it with LEFT JOIN ... UNION ... RIGHT JOIN.

7. ⚠️ Common Mistakes

1. Confusing ON with WHERE

Wrong: Putting the join condition in WHERE instead of ON when using an outer join.

-- ❌ This turns the LEFT JOIN into an INNER JOIN!
SELECT *
FROM employees e
LEFT JOIN departments d
WHERE e.dept_id = d.dept_id;

-- ✅ Correct: use ON for the join condition
SELECT *
FROM employees e
LEFT JOIN departments d
  ON e.dept_id = d.dept_id;

When you filter in WHERE, rows with NULL on the right side get eliminated because NULL = anything is never true. The ON clause controls how rows are matched; WHERE filters after the join.

2. Forgetting to handle NULL values

After a LEFT or RIGHT join, unmatched columns contain NULL. If you don't account for this, your results may look wrong or your aggregations may be off.

-- ❌ COUNT(dept_name) skips NULLs, giving a misleading count
SELECT COUNT(dept_name) FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;

-- ✅ Use COALESCE or COUNT(*) to handle NULLs
SELECT COUNT(*) FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;

-- Or replace NULLs with a label
SELECT e.name, COALESCE(d.dept_name, 'Unassigned') AS dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;

3. Accidentally creating a Cartesian product

Forgetting the ON clause (or using a condition that's always true) produces a Cartesian product — every row from one table paired with every row from the other.

-- ❌ No ON clause = Cartesian product (4 × 4 = 16 rows!)
SELECT *
FROM employees e
JOIN departments d;

-- ✅ Always specify the join condition
SELECT *
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id;

4. Joining on non-unique columns

If the join column has duplicates, you'll get more rows than expected. Always join on a primary key or a unique column.

-- ❌ If dept_name has duplicates, you get extra rows
SELECT *
FROM employees e
JOIN departments d ON e.dept_name = d.dept_name;

-- ✅ Join on the unique key
SELECT *
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id;

5. Assuming RIGHT JOIN is supported everywhere

MySQL does not support RIGHT JOIN. PostgreSQL, SQL Server, and Oracle do. If you need portability, rewrite as a LEFT JOIN by swapping the table order.

-- ❌ Not supported in MySQL
SELECT * FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.dept_id;

-- ✅ Portable: swap the tables and use LEFT JOIN
SELECT * FROM departments d
LEFT JOIN employees e ON e.dept_id = d.dept_id;

6. Using = to compare NULL values

In SQL, NULL = NULL evaluates to UNKNOWN, not TRUE. This means rows with NULL keys will never match in a join.

-- ❌ NULLs will never match
SELECT * FROM t1 JOIN t2 ON t1.id = t2.id;

-- ✅ Use IS to handle NULLs
SELECT * FROM t1 JOIN t2 ON t1.id IS NOT DISTINCT FROM t2.id;
-- or
SELECT * FROM t1 JOIN t2 ON (t1.id = t2.id OR (t1.id IS NULL AND t2.id IS NULL));

8. Practice Exercises

  1. Write a query that lists all employees and their department names, showing "Unassigned" for employees without a department.
  2. Write a query that finds departments with no employees.
  3. Write a query that returns all employees and departments, even if they don't match (FULL JOIN).
  4. Given a orders table, write a query that lists all customers and their total order count, including customers with zero orders.
